## 7. 템플릿과 제네릭 프로그래밍

### 템플릿이 필요한 이유
- 타입별로 오버로딩을 일일이 만드는 대신, 임의의 자료형에 대해 하나의 템플릿으로 로직을 구현
```cpp
template <typename T>
T Get_Max(T a, T b) { return (a > b) ? a : b; }
```

### 템플릿 인스턴스화 — 시점의 정확한 의미
- 템플릿은 **정의 시점**이 아니라, 특정 타입으로 **호출되는 시점(컴파일 타임)**에 그 타입에 맞는 실제 함수 코드가 생성됨(인스턴스화)
- 예: `Get_Max(3,7)`은 `T=int`로 문제없이 인스턴스화되지만, `operator>`가 없는 `Player` 타입으로 `Get_Max(p1,p2)`를 호출하면 **그 호출 지점에서** 컴파일 에러 발생
- "컴파일 타임 호출(인스턴스화)"과 "런타임 함수 호출"은 완전히 다른 개념 — 전자는 컴파일러가 코드를 만들어내는 것, 후자는 프로그램 실행 중 CPU가 그 코드로 점프하는 것

### 템플릿(컴파일 타임 다형성) vs virtual 함수(런타임 다형성)
| | 템플릿 | virtual 함수 |
|---|---|---|
| 성능 | 빠름 (직접 호출, 인라인 가능, 간접 참조 없음) | vptr→vtable 조회로 인한 간접 참조 오버헤드 |
| 실행 파일 크기 | 호출된 타입마다 코드 중복 생성(코드 팽창) — 소수 타입이면 무시 가능, 광범위한 타입 조합(수학 라이브러리 등)이면 실무에서 실제 이슈가 됨 | 함수 코드는 클래스당 하나로 공유되어 가벼움 |
| 유연성 | 타입이 컴파일 타임에 확정되어야 함 | 런타임에 타입이 바뀌거나 다형적 컨테이너에 섞일 수 있음 |

**선택 기준**: "이 타입이 실행 중에 바뀌거나 같은 컨테이너/슬롯에 여러 타입이 섞일 필요가 있는가?" → virtual. "타입이 컴파일 타임에 이미 확정되고 성능이 중요한가?" → 템플릿.

**게임 엔진 예시**:
- `vector<Enemy*>`로 다양한 적을 순회하며 `Update()`/`Attack()` 호출 → virtual (런타임에 타입 다양성 필요)
- `Vector3`/`Vector4`의 float/double 버전 → 템플릿 (컴파일 타임에 타입 확정, 매 프레임 호출되는 수학 연산이라 성능 중요)
- 무기 교체 시스템(플레이어가 런타임에 무기를 바꿈) → virtual (동일 인터페이스로 다른 동작)
- 범용 컨테이너 클래스 → 템플릿 (타입 안전성, 컴파일 타임에 원소 타입 확정)

### (참고) 동적 바인딩이 일어나는 조건
- 핵심: **포인터/참조를 통해 virtual 함수를 호출하는가**
  - 객체를 직접 다룰 때(`Derived d; d.Move();`) → 실제 타입을 컴파일러가 100% 확신 가능 → 동적 바인딩 불필요, devirtualization 최적화 대상
  - 포인터/참조로 다룰 때(`Base* p = ...; p->Move();`) → 정적 타입과 실제 타입이 다를 수 있어 원칙적으로 동적 바인딩 발생
- `Derived* pD = new Derived();`도 포인터인 이상 원칙적으로 vptr을 거침 (컴파일러가 흐름을 완전히 추적 가능한 단순한 경우엔 예외적으로 devirtualization 최적화 가능)

### 템플릿 특수화 (template specialization)
- 특정 타입에 대해서만 일반 템플릿과 다른 구현이 필요할 때 사용
```cpp
template <typename T>
T Get_Max(T a, T b) { return (a > b) ? a : b; }

// const char*에 대한 완전 특수화 — 주소 비교 대신 strcmp로 내용 비교
template <>
const char* Get_Max<const char*>(const char* a, const char* b) {
    return (strcmp(a, b) > 0) ? a : b;
}
```
- 컴파일러는 호출된 타입에 대한 특수화 버전이 있는지 먼저 찾고, 있으면 우선 사용, 없으면 일반 템플릿 인스턴스화
- `std::string`은 `operator>` 등이 이미 사전순 비교로 오버로딩되어 있어 특수화 없이 일반 템플릿 그대로 정상 동작. `const char*`는 raw pointer라 언어가 정한 "주소 비교" 의미를 벗어날 수 없어 특수화가 필요했던 것

### 비타입 템플릿 매개변수 (non-type template parameter)
```cpp
template <typename T, size_t N>
class FixedArray {
    T m_data[N];
public:
    T& operator[](size_t index) { return m_data[index]; }
};

FixedArray<int, 10> intArr;
```
- `T`(타입 템플릿 매개변수)와 달리 `N`은 **값**을 받는 템플릿 매개변수
- `T m_data[N];`처럼 배열을 멤버로 가지려면 `N`이 컴파일 타임 상수여야 함(스택 할당은 크기가 컴파일 타임에 확정되어야 하므로) → 일반 생성자 매개변수(런타임 값)로는 불가능, 템플릿 매개변수로 받아야 각 `N`마다 별도 클래스로 인스턴스화되어 컴파일 타임에 크기가 고정됨
- `std::array<T, N>`이 이 원리로 동작 (힙 할당 없는 고정 크기 컨테이너)
- FixedArray vs vector: FixedArray는 스택 할당(힙 할당 비용 없음, 포인터 역참조 없이 직접 접근, 캐시 지역성 좋음) ↔ 크기가 런타임에 안 바뀜. vector는 힙 할당 필요(간접 참조 1단계 추가) ↔ 런타임에 유연하게 크기 변경 가능

### (참고) vector의 포인터 간접 참조와 캐시
- `vec[0]` 접근 시: (1) vector 객체에서 `m_data` 포인터 읽기 → (2) 그 포인터가 가리키는 실제 데이터 접근, 2단계 메모리 접근
- range-based for문에서는 `m_data` 포인터 조회(간접 참조)가 순회 **시작 시 한 번**만 일어나고(`begin()` 호출 시), 이후 반복은 이미 확보한 주소를 이용
- vector의 데이터 자체는 힙에서 연속 메모리로 할당되므로, 일단 시작하면 순차 접근(iteration) 자체의 캐시 효율은 좋음 — "매 원소 접근마다 계속 비용이 붙는다"가 아니라 "최초 접근 시 간접 참조 한 단계가 추가된다"가 정확한 이해

### 템플릿은 왜 헤더에 선언+구현을 함께 넣는가
- 일반 함수처럼 헤더에 선언만, cpp에 구현만 나누면: 호출하는 `.cpp`를 컴파일할 때 템플릿의 실제 구현이 안 보여 인스턴스화를 못 하고, 링커가 나중에 그 인스턴스(`Get_Max<int>` 등)를 찾지 못해 **"undefined reference" 링크 에러** 발생
- 이유: 템플릿 인스턴스화는 호출부가 컴파일되는 시점에 일어나야 하는데, 그러려면 그 호출부가 템플릿의 실제 구현을 볼 수 있어야 함
- 해결: 헤더에 선언+구현을 통째로 넣어서, include하는 모든 `.cpp`가 구현을 직접 보고 그 자리에서 인스턴스화할 수 있게 함

### inline과 ODR(One Definition Rule) 예외
- `inline`의 두 가지 의미:
  1. 인라인 확장(함수 호출부에 코드를 복사해 호출 오버헤드 제거) — 컴파일러 최적화 힌트일 뿐, 실제 적용 여부는 컴파일러 재량
  2. **링크 규칙 지정** — "이 함수 정의가 여러 번역 단위(.cpp)에 중복 존재해도 링크 에러로 취급하지 않는다"는 ODR 예외 허가
- 템플릿에서 문제가 되는 건 2번 의미: 여러 `.cpp`가 같은 헤더를 include해서 각자 같은 템플릿을 인스턴스화하면 중복 정의가 생기는데, **템플릿으로부터 인스턴스화된 함수는 개발자가 `inline`을 안 붙여도 표준이 자동으로 inline(ODR 예외) 취급**해서 링크 에러가 안 남 (링커가 중복 정의 중 하나만 골라 사용)
- 자동으로 inline 취급되는 경우: ① 템플릿 함수/클래스, ② 클래스 정의 내부에서 직접 구현한 멤버 함수 — 둘 다 "헤더에 구현을 넣는 게 자연스럽거나 불가피한 경우"라 언어가 자동으로 안전장치 제공
- 일반 자유 함수를 헤더에 구현째로 넣을 경우: 자동 특혜 없음 → 여러 `.cpp`에서 include 시 직접 `inline`을 붙이지 않으면 "multiple definition" 링크 에러

### 가변 인자 템플릿 (variadic template)
```cpp
template <typename... Args>
void Log(Args... args) {
    (std::cout << ... << args) << std::endl; // fold expression
}
```
- `Args`는 "임의 개수의 타입들의 목록"(파라미터 팩) — 호출마다 그 인자 조합에 맞는 함수가 별도로 인스턴스화됨
- 가변 인자 템플릿 ≠ 퍼펙트 포워딩: 가변 인자 템플릿은 "인자 개수가 가변적"이라는 문제를 해결, 퍼펙트 포워딩(`std::forward`, `T&&`)은 "인자를 다음 함수로 넘길 때 원래의 lvalue/rvalue 성격을 유지"하는 문제를 해결. 서로 다른 기법이며 `make_unique`, `emplace_back` 등에서 함께 자주 쓰임

**사용 예시**: 로그 함수, `vector::emplace_back`(생성자 인자를 그대로 전달해 복사/이동 없이 컨테이너 내부에 직접 생성), 팩토리 함수(`Make_GameObject<T>(Args&&... args)`), 이벤트 시스템(`Event<int, string>`)

**주의점**:
- 재귀 인스턴스화 방식(구형)은 코드 팽창을 유발할 수 있음
- 컴파일 에러 메시지가 길고 원인 추적이 어려움
- 타입 검증이 호출 시점에야 이루어짐 (C++20 concept로 더 이른 시점 검증 가능)
- 디버깅 난이도가 일반 함수보다 높음
