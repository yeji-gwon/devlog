## 8. static 키워드

### static의 3가지 의미 — 공통 본질
- **본질**: "이 데이터/코드의 생명주기 또는 가시성을, 기본 규칙과 다르게 만든다"
  - 클래스 static 멤버: 보통 인스턴스에 속하는데 → 클래스 자체에 속하게(더 넓게 공유)
  - 함수 내부 static 지역 변수: 보통 함수 호출마다 사라지는데 → 계속 살아있게(생명주기 연장)
  - 파일 스코프 static: 보통 전역적으로 보이는데 → 이 파일 안에서만 보이게(더 좁게 숨김)

### 1) 클래스 static 멤버 변수/함수
```cpp
class Enemy {
    static int s_count; // 선언
public:
    Enemy() { s_count++; }
    static int Get_Count() { return s_count; } // static 멤버 함수
};
int Enemy::s_count = 0; // 정의 (실제 메모리 확보)
```
- 인스턴스마다 생성되는 일반 멤버 변수와 달리, **클래스에 속한 하나의 변수**로 모든 인스턴스가 공유
- static 멤버 함수는 **this 포인터가 없음** → 일반(non-static) 멤버 변수에 접근 불가, static 멤버만 접근 가능
- **선언(헤더)과 정의(cpp) 분리 이유**: 헤더에서 바로 정의하면 그 헤더를 include하는 모든 `.cpp`마다 별도의 메모리 공간이 생겨버려 "클래스 전체에 하나"라는 의미가 깨짐 → 헤더는 존재만 선언, 단 하나의 `.cpp`에서 실제 정의(메모리 확보 + 초기화)
- **초기화 시점**: `main()` 실행 전 (해당 클래스를 실제로 쓰든 안 쓰든 무조건 초기화됨)

### 2) 함수 내부 static 지역 변수
```cpp
void Foo() {
    static int callCount = 0; // 처음 도달할 때 딱 한 번만 초기화
    callCount++;
    cout << callCount << endl;
}
Foo(); Foo(); Foo(); // 1, 2, 3 출력
```
- 일반 지역 변수(스택, 함수 리턴 시 소멸)와 달리 **데이터 영역(정적 저장소)**에 할당되어 프로그램 종료까지 유지
- **초기화 시점**: 그 코드에 **처음 도달할 때** 딱 한 번 (지연 초기화, lazy initialization) — 함수를 한 번도 호출 안 하면 초기화 자체가 안 일어남
- 클래스 static 멤버(프로그램 시작 시 무조건 초기화)와 정확히 대비됨

### 싱글턴 패턴과 스레드 안전성 (Meyer's Singleton)
```cpp
class GameManager {
public:
    static GameManager& Get_Instance() {
        static GameManager instance; // 함수 내부 static 활용
        return instance;
    }
private:
    GameManager() {}
};
```
- **C++11부터 표준이 "함수 내부 static 변수의 초기화는 스레드 안전해야 한다"고 명시적으로 의무화** (§6.7)
- 컴파일러가 내부적으로 뮤텍스 기반 이중 확인 잠금(double-checked locking)과 플래그를 자동 삽입 → 여러 스레드가 동시에 처음 호출해도 생성자는 정확히 한 번만 실행됨
- **반면 수동 포인터 방식**(`if (s_instance == nullptr) s_instance = new GameManager();`)은 "체크"와 "생성" 사이에 다른 스레드가 끼어들 수 있는 레이스 컨디션(race condition) 존재 → 인스턴스가 두 개 생길 위험
- MSVC는 VS2015부터 이 보장을 완전히 지원 (VS2013 이전은 불완전)

### 3) 파일 스코프 static (내부 링키지)
```cpp
// Helper.cpp
static int Calculate_Damage(int base, float multiplier) { ... } // 이 파일 안에서만 접근 가능

// AI.cpp
static int Calculate_Damage(int base, float multiplier) { ... } // 완전히 별개 함수, 충돌 없음
```
- 클래스 멤버가 아닌 자유 함수/전역 변수에 `static`을 붙이면 **내부 링키지(internal linkage)**를 가짐 → 그 번역 단위(.cpp) 밖에서는 존재 자체를 모름
- `static` 없이 같은 이름의 함수를 여러 `.cpp`에서 정의하면 링커가 "multiple definition" 에러를 냄 (템플릿을 헤더에 구현할 때와 유사한 문제, 해결 방식은 다름 — 템플릿은 inline 취급으로 중복 허용, 이건 애초에 파일 밖에서 안 보이게 격리)
- 실무적 이점: 이름 충돌 방지, "이 함수는 이 파일의 구현 세부사항일 뿐"이라는 의도 명시(캡슐화)

### Helper 함수 구현 방법 4가지
| 방법 | 특징 | 용도 |
|---|---|---|
| 헤더 public 선언 + cpp에 static 헬퍼 숨기기 | 공개 함수 몇 개 + 내부 로직 은닉 | 외부 인터페이스는 적고 내부 계산이 복잡할 때 |
| 네임스페이스로 묶기 (`namespace MathHelper { ... }`) | 상태 없는 유틸 함수 모음에 표준적 | 가장 일반적으로 권장되는 방식 |
| static 멤버만 있는 "static 클래스" (생성자 `= delete`) | 네임스페이스와 유사, 상수도 함께 묶기 좋음 | 클래스 중심 컨벤션 프로젝트 |
| 익명 네임스페이스 (`namespace { ... }`) | 파일 스코프 static과 동일 효과, 여러 개를 한번에 숨김 | 한 파일 안에 숨길 대상이 여럿일 때 |

## 9. 예외 처리

### throw 발생 시 흐름
```cpp
void Load_File(const string& path) {
    if (path.empty()) throw std::invalid_argument("path is empty");
}
```
- `throw` 실행 즉시 함수 실행 중단, 이후 코드는 실행되지 않음
- 호출 스택을 거슬러 올라가며(stack unwinding) 타입이 일치하는 `catch`를 탐색
- 일치하는 `catch`를 찾으면 그 블록 실행 후 `try-catch` 다음 코드부터 정상 진행
- **아무도 못 잡으면 `std::terminate()` 호출로 프로그램 강제 종료** (noexcept 약속 위반 시와 동일한 결말)

### 예외를 참조로 잡는 이유
```cpp
catch (const std::exception& e) { ... } // 참조로 잡는 것이 관례
```
1. **성능**: 값으로 받으면 복사 비용 발생, 참조는 복사 없음
2. **슬라이싱(object slicing) 방지** — 더 중요한 이유
   - 파생 예외 클래스(`MyException`)를 부모 타입(`std::exception`)으로 **값으로** 받으면, 부모 타입 크기만큼만 복사되어 파생 클래스만의 멤버(`m_detail` 등)가 통째로 잘려나감
   - 결과: `e.what()` 호출 시 virtual 함수임에도 부모의 기본 구현이 호출됨 (동적 바인딩이 깨짐)
   - 참조로 받으면 복사 자체가 없어 원본 객체를 그대로 가리키므로 virtual 함수가 정상적으로 파생 클래스 버전을 찾아감
   - 5번 세션의 "포인터/참조=동적 바인딩, 값=정적 타입" 원리가 catch에도 동일 적용됨
