
#### 1. 객체지향 프로그래밍(OOP, Object Oriented Programming)

- 정의
  데이터(멤버 변수)와 그 데이터를 처리하는 함수(멤버 함수)를 하나의 객체로 묶어서 프로그램을 설계하는 프로그래밍 패러다임
- 핵심 아이디어
	- 객체는 자신의 데이터와 행동(함수)를 스스로 **책임짐**→ 캡슐화
	- **복잡한 내부는 감추고** 필요한 것만 노출함 → 추상화
	- 객체 간의 관계(상속)를 통해 코드를 **재사용하고 확장함** → 상속
	- **같은 인터페이스**로 다양한 객체가 **서로 다르게 동작함** → 다형성
	- 결과적으로 재사용성, 유지보수성, 확장성을 높임


#### 2. 4대 특징

1. 캡슐화 (Encapsulation)
	- 정의: 데이터와 함수를 하나로 묶고, 외부에는 필요한 인터페이스만 노출하며 내부 구현은 숨기는 것
	- 초점: **접근과 책임의 통제** (멤버 변수는 멤버 함수 내부에서 관리할 것, 외부에서 관심을 두지 않아도 되고, 함수 호출만 하면 됨)
	- 방법: private/protected로 멤버 변수를 감추고, public 함수로만 외부 접근 허용
	- 효과: **결합도 감소** (객체 내부 구현이 바뀌어도 외부 코드에 영향이 없음) → 유지보수 용이

2. 추상화 (Abstraction)
	- 정의: 복잡한 내부 구현은 감추고, 필요한 핵심 기능만 인터페이스로 드러내는 것
	- 초점: **복잡성의 단순화** (복잡한 건 객체 내부에서 처리할 테니, 외부에선 호출할 기능만 알면 됨)
	- 방법: 추상 클래스(순수가상함수 포함), 인터페이스 역할의 클래스
	- 효과: 복잡성 감소 
		- 학습/사용 비용 감소: 사용하는 쪽은 인터페이스만 알면 됨 (내부 구현 몰라도 됨)
		- 결합도 감소: 내부 구현이 바뀌어도 인터페이스만 유지되면 사용하는 쪽 코드는 영향 없음 (캡슐화와 겹침_)
		- 확장 용이: 인터페이스만 지키면 새로운 구현체를 계속 추가 가능 (다형성과 연결)
		- 결과적으로 유지보수성과 개발 생산성 향상
	- 캡슐화와 차이: 캡슐화는 누가 접근할 수 있는가를 통제하는 것, 추상화는 무엇을 보여줄 것인가를 설계하는 것. 다만 둘 다 결과적으로 외부가 내부 구현에 의존하지 않게 하여 결합도를 낮추고 유지보수를 쉽게 한다는 점에서 공통점.
	- 예시:
		- 게임 엔진을 사용할 때, 개발자는 물리 연산이나 렌더링 파이프라인 내부 구현을 몰라도 `RigidBody.AddForce()`, `Mesh.Draw()` 같은 함수를 호출해서 조립하는 방식으로 로직을 짤 수 있음. 엔진을 만드는 것 자체가 추상화 계층을 설계하는 작업이라 볼 수 있음.
		- EventSystem을 예시로 들면, 구독하는 쪽과 발생하는 쪽은 `Subscribe` / `Publish`라는 인터페이스만 알면 됨. 내부적으로 `weak_ptr`로 구독자 생존 여부를 어떻게 관리하는지, 서로 다른 타입의 콜백을 어떻게 저장하는지, 죽은 구독자를 언제 정리하는지 같은 복잡한 구현은 전혀 몰라도 됨. 이 시스템의 핵심 목적 자체가 "발생자와 구독자가 서로의 존재를 몰라도 되게 디커플링하는 것"인데, 이게 가능한 이유가 바로 `Publish` / `Subscribe`라는 추상화된 인터페이스 덕분

3. 상속 (Inheritance)
	- 정의: 기존 클래스(부모/베이스)의 속성과 기능을 새로운 클래스(자식/파생)가 물려받는 것
	- 목적: **코드 재사용**, 공통 기능을 부모에 정의하고 자식은 차이점만 구현
	- 주의점: 상속을 남발하면 계층이 깊어져서 오히려 유지보수 어려워짐 → is-a 관계가 명확할 때만 사용
	- 관련 개념: 상속 vs 컴포지션

4. 다형성 (Polymorphism)
	- 정의: **같은 인터페이스**로 서로 다른 객체가 서로 **다르게 동작**하는 것
	- 종류:
		- 컴파일타임 다형성: 함수 오버로딩, 연산자 오버로딩 (정적 바인딩)
		- 런타임 다형성: 가상함수를 통한 오버라이딩 (동적 바인딩, vtable/vptr)
	- 효과: 부모 타입 포인터/참조로 자식 객체를 다루면서 각기 다른 동작을 실행 가능 → 확장에 유연



> [!note]- 객체지향이란
> 객체지향이란 데이터와 그 데이터를 관리하는 함수를 객체로 묶어, 객체 간의 상호작용으로 프로그래밍하는 패러다임입니다. 캡슐화, 추상화, 상속, 다형성이라는 특징을 통해 재사용성과 유지보수성을 높입니다. 
> 
> 저는 자체 DX11 엔진을 설계하면서 이 부분을 직접 고민해볼 기회가 있었습니다.
> 
> 예를 들어 FSM을 설계할 때 `IState`라는 추상 클래스로 `Enter`, `Update`, `Exit`이라는 인터페이스만 강제하고, `Idle`이나 `Attack`같은 구체적인 상태는 이를 상속받아 각자 다륵 구현하도록 했습니다. 그 결과 FSM 매니저는 지금 어떤 상태인지 몰라도 `Update()`만 호출하면 되고, 나중에 새로운 상태가 추가돼도 기존 코드는 건드릴 필요가 없었습니다. 이 과정에서 상속을 통한 재사용성, 추상화를 통한 인터페이스 노출, 다형성을 통한 확장성을 함께 체감했습니다.
> 
> 예를 들어 옵저버 패턴 기반의 이벤트 시스템을 직접 설계하면서 이 부분을 체감했습니다. 사용자는 `Subscribe`와 `Publish`라는 인터페이스만 알면 되고, 내부에서 `weak_ptr`로 구독자의 생존 여부를 관리하거나, 콜백의 타입을 소거해서 저장하거나, 죽은 구독자를 정리하는 것 같은 복잡한 로직은 몰라도 됩니다. 이런 추상화 덕분에 발행자와 구독자가 서로의 존재를 몰라도 동작하는 디커플링이 가능했습니다.

> [!note]- 객체지향의 장단점
> 객체지향의 장점은 유지보수성과 협업 효율성이 높아진다는 점이라고 생각합니다. 팀 프로젝트에서 오버쿡스 스타일의 상호작용 시스템을 만들 때, 저는 상호작용 오브젝트 쪽을, 팀원은 플레이어 쪽을 담당했는데, `IPlace`, `IProcess` 같은 인터페이스를 먼저 정의해두고 각자 구현에 들어갔습니다. 그 결과 팀원은 프라이팬이나 도마 같은 스테이션이 내부적으로 어떻게 조리 진행도를 계산하는지 몰라도, `Set_Place()`나 `Enter_Process()` 같은 인터페이스만 호출해서 플레이어 상호작용 로직을 짤 수 있었고, 저도 플레이어 입력 로직을 몰라도 스테이션 쪽 구현에만 집중할 수 있었습니다. 이렇게 인터페이스로 서로의 구현을 분리하면서 결합도를 낮추고 병렬 개발이 가능했던 게 객체지향의 실질적인 장점이라고 느꼈습니다.
> 
> 객체지향의 단점은 성능 측면에서 나타날 수 있다고 생각합니다. 먼저 가상함수는 vtable을 통한 간접 호출 방식이라 일반 함수 호출보다 오버헤드가 있고, 컴파일 타임에 실제 타입을 알 수 없어서 인라인 최적화도 어렵습니다. 그리고 오브젝트 수가 매우 많은 대규모 시뮬레이션의 경우, 객체를 힙에 개별 할당하면서 메모리상에 데이터가 흩어지게 되는데, 위치·체력·상태가 한 객체에 뭉쳐 있는 구조라서 필요한 데이터만 갱신하려 해도 캐시 라인에 불필요한 데이터까지 함께 로드되어 캐시 미스가 잦아질 수 있습니다. 이런 경우에는 데이터를 배열 단위로 묶어 연속된 메모리에 배치하는 데이터 지향 설계를 함께 고려하기도 한다고 알고 있습니다.

> [!note]- 절차지향과 비교
> 절차지향과 객체지향의 가장 큰 차이는 데이터와 함수의 관계입니다. 절차지향은 함수와 데이터가 분리되어 있어서, 함수가 데이터를 매개변수로 받아 순차적으로 처리하는 방식입니다. 반면 객체지향은 데이터와 그 데이터를 다루는 함수를 하나의 객체로 묶어서, 객체가 자신의 데이터에 대한 접근을 스스로 통제합니다. 이 차이 때문에 객체지향에서는 캡슐화를 통한 결합도 감소, 상속과 다형성을 통한 재사용성·확장성 확보가 가능해지고, 대규모 프로젝트에서 유지보수가 쉬워집니다.

> [!note]- 언제 사용
> 객체 간 상호작용이 복잡하고 상태 관리가 필요한 대규모 프로젝트에서는 객체지향을 통해 결합도를 낮추고, 재사용성과 확장성을 높여 생산성을 높일 수 있습니다. 반면 소규모 프로젝트나 단순한 데이터 처리 로직에서는 굳이 객체로 묶는 오버헤드 없이 절차지향으로 빠르게 작성하는 게 효율적일 수 있습니다. 다만 파티클 시스템처럼 오브젝트 수가 매우 많고 성능이 극도로 중요한 경우에는, 캡슐화의 이점보다 캐시 지역성이 우선시되어 데이터 지향 설계 같은 다른 접근을 고려하기도 합니다.

> [!note]- 객체, 클래스, 인스턴스
> 클래스는 객체를 만들기 위한 설계도로, 데이터와 함수의 구조를 정의하는 문법적 틀입니다. 객체는 그 클래스를 바탕으로 정의된 데이터와 함수의 논리적 단위이고, 인스턴스는 그 객체가 실제로 메모리에 할당되어 실행 중에 존재하는 실체를 말합니다. 예를 들어 `CPlayer`가 클래스라면, `CPlayer`로 표현되는 대상 자체가 객체이고, `new CPlayer()`로 메모리에 생성되어 실제로 동작하는 `player1`이 인스턴스입니다.
> 실무에서는 사실 객체와 인스턴스를 거의 같은 의미로 혼용해서 쓰는 경우도 많지만, 엄밀히 구분하면 객체는 개념적 단위, 인스턴스는 그게 메모리에 실체화된 상태로 이해하고 있습니다.

> [!note]- 클래스와 구조체 비교
> C++에서 클래스와 구조체는 문법적으로는 거의 동일합니다. 차이는 두 가지인데, 첫째는 기본 접근 제어자로 클래스는 private, 구조체는 public이 기본값입니다. 둘째는 상속 시 기본 접근 지정자인데, 클래스는 private 상속이, 구조체는 public 상속이 기본입니다. 이런 문법적 차이 외에는 본질적으로 동일하지만, 관습적으로 구조체는 단순히 데이터를 묶는 용도(POD, Plain Old Data)로 사용하고, 클래스는 캡슐화나 상속 같은 객체지향적 설계가 필요할 때 사용합니다.
