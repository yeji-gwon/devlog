## 5. 가상 함수와 다형성

### 동적 바인딩 (vptr / vtable)
- non-virtual 함수: 컴파일 타임에 정적 타입 기준으로 호출할 함수가 결정됨
- virtual 함수: 런타임에 실제 객체의 vptr → vtable을 참조해서 오버라이드된 함수 주소로 호출 (동적 바인딩)
- vtable: **클래스당 하나** (모든 인스턴스가 공유)
- vptr: **객체(인스턴스)마다 하나씩** 붙어서 자신의 클래스 vtable을 가리킴

### virtual 함수의 비용
- 메모리: 객체마다 vptr 8바이트 추가
- 성능: 함수 호출 시 vptr → vtable → 함수 주소 조회의 간접 참조 비용 (인라인화도 어려워짐)
- 그래서 다형적으로 쓰일 가능성이 없는 클래스라면 굳이 virtual을 붙일 필요 없음

### virtual 소멸자
- 기반 클래스 포인터로 파생 클래스 객체를 `delete`할 때, 소멸자가 virtual이 아니면 **정적 타입(기반 클래스)의 소멸자만 호출**되고 파생 클래스 소멸자는 스킵됨 → 파생 클래스가 가진 자원(동적 할당, 스마트 포인터 멤버 등)이 정리되지 않아 누수 발생
- **Rule of 0(스마트 포인터로 자원 관리 위임)을 따르더라도 이 문제는 막아주지 못함** — Rule of 0은 "자원을 올바르게 다루는가"의 문제, virtual 소멸자는 "다형적 delete 시 어떤 소멸자 체인이 실행되는가"의 문제로 서로 독립적
- **virtual 소멸자가 필요한 조건**: "상속 관계가 있다"가 아니라 **"기반 클래스 포인터/참조로 파생 객체를 delete할 가능성이 실제로 있는가"**
  - 코드 재사용만을 위한 상속(믹스인, CRTP, 유틸리티 베이스 등)은 다형적으로 다룰 일이 없으므로 virtual 소멸자 불필요
- 다중 상속 시 기반 클래스들의 생성/소멸 순서는 **상속 목록에 적힌 순서** (소멸은 그 역순)
- 다중 상속에서 한쪽 기반 클래스만 virtual 소멸자를 갖고 다형적으로 쓰이는 진입점 역할을 하면, 나머지 기반 클래스는 virtual이 없어도 안전 (그 기반 클래스를 직접 포인터로 delete하는 경로가 없다면)

### 소멸자 호출 순서
- 생성: 기반 클래스 → 파생 클래스 순
- 소멸: 파생 클래스 → 기반 클래스 순 (생성의 역순)
- 이유: 파생 클래스가 기반 클래스의 자원/멤버를 사용하고 있을 수 있으므로, 안전하게 파생 클래스부터 정리

### 순수 가상 함수와 추상 클래스
- `virtual 반환형 함수명() = 0;` → 순수 가상 함수. 구현부 없이 파생 클래스에서 반드시 구현하도록 강제
- 순수 가상 함수를 하나라도 가진 클래스 → **추상 클래스**, 직접 인스턴스화 불가(컴파일 에러)
- **선택 기준**: "이 함수가 없으면 파생 클래스가 의미상 말이 안 되는가?"
  - 그렇다 → 순수 가상으로 강제 (구현 누락 시 컴파일 에러로 즉시 발견)
  - 아니다, 합리적인 기본 동작이 있다 → 일반 virtual + 기본 구현 (선택적 오버라이드)
- 만약 순수 가상 대신 빈 기본 구현을 줬다면: 파생 클래스가 구현을 빠뜨려도 컴파일은 통과되고, 런타임에 "조용히 아무 일도 안 일어나는" 버그로 이어짐 → 발견도 원인 추적도 어려움
- 예시: State 패턴(`Update()`는 순수 가상, `Enter()`/`Exit()`는 기본 구현), 무기 시스템(`Fire()`/`Get_Damage()`는 순수 가상, `Reload()`는 기본 구현)

### 추상 클래스 vs 인터페이스 (C++ 관례)
| | 인터페이스 (관례) | 추상 클래스 |
|---|---|---|
| 멤버 변수 | 없음 | 있을 수 있음 |
| 구현된 함수 | 없음 (전부 순수 가상) | 일부 있음 (공통 로직 재사용) |
| 목적 | "이런 행동을 할 수 있다"는 계약만 정의 | 공통 상태+로직을 재사용하며 일부만 강제 |
| 다중 상속 | 여러 개 동시 구현 흔함 | 보통 단일 상속으로 계층 구성 |

### 구조 설계 시 관계 구분 — IS-A vs CAN-DO vs HAS-A
- **상속 (IS-A)**: "이것은 ~의 한 종류다" — 공통 특성/로직을 물려받음 (`Enemy : public GameObject`)
- **인터페이스 상속 (CAN-DO)**: "이것은 ~할 수 있어야 한다" — 서로 무관한 클래스들에 공통 행동을 **강제**. 타입 자체에 컴파일 타임으로 고정되는 규칙일 때 사용 (`Enemy : public IDamageable`)
- **추상 클래스 상속**: 같은 계열 안에서 공통 골격은 공유하되 핵심 동작만 파생 클래스마다 다르게 강제 (IS-A의 특수한 형태)
- **컴포넌트 (HAS-A)**: "이것은 ~을 가지고 있다" — 상속이 아니라 멤버로 소유, 런타임에 조립/제거 가능 (`Enemy`가 `HealthComponent`를 멤버로 가짐)

### CAN-DO vs HAS-A 판단 기준
- "이 오브젝트 타입이라면 예외 없이 항상 성립해야 하는 규칙인가?" → 인터페이스로 강제 (컴파일 타임 보장, 런타임에 뗄 수 없음)
- "오브젝트마다 있을 수도 없을 수도 있고, 런타임에 바뀔 수도 있는 특성인가?" → 컴포넌트로 조립 (런타임 유연성)
- 실무에서는 보통 컴포넌트 시스템을 기본 골격으로 쓰고, 타입에 고정적으로 강제하고 싶은 규칙이 있을 때만 인터페이스를 추가
