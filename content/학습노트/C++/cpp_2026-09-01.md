## 4. 생성자/소멸자와 복사/이동 시맨틱

### 얕은 복사 문제
- 동적 할당 멤버(raw pointer)를 가진 클래스에서 복사 생성자/대입 연산자를 정의하지 않으면, 컴파일러가 만든 기본 버전이 멤버 값 그대로 복사(얕은 복사)함
- 두 인스턴스가 같은 힙 주소를 가리키게 되어 → 댕글링 포인터, 이중 해제(double free) 문제 발생
- 해결: 복사 생성자/대입 연산자를 직접 정의(깊은 복사)하거나, `= delete`로 복사 자체를 금지

### 깊은 복사 vs 이동
- 깊은 복사: 새로 동적 할당하고 값을 그대로 복사 → 원본은 그대로 살아있음
- 이동: 포인터(소유권)만 옮기고 원본은 nullptr 처리 → 원본은 더 이상 유효하지 않음, 재할당/복사 비용 없음
- 함수 반환, vector 재할당 등 "원본을 더 이상 쓸 필요 없는" 상황에서 이동이 훨씬 효율적

### noexcept와 vector 재할당
- vector가 재할당할 때, 원소를 이동시킬지 복사시킬지는 이동 생성자에 `noexcept`가 붙어있는지로 결정
- 복사 중 예외 발생: 원본(oldArr)은 안 건드렸으니 그대로 남아있음 → 새로 만들다 만 원소들만 정리하고 새 메모리 해제 → 롤백 가능 (강한 예외 보장)
- 이동 중 예외 발생(가정): 이미 옮긴 원소는 원본이 파괴(빈 껍데기)된 상태 → 되돌릴 수 없음 → 롤백 불가능
- 그래서 vector는 이동 생성자가 noexcept로 보장되지 않으면, 위험을 피해 아예 처음부터 복사를 선택함 (`std::move_if_noexcept`)

### noexcept 키워드
- "이 함수는 예외를 던지지 않는다"는 프로그래머의 약속 (컴파일러가 내부 로직까지 검증해주진 않음)
- 컴파일러는 이 약속을 믿고 예외 처리용 부가 코드(스택 언와인딩 대비)를 생략 → 미세한 성능 이득
- 약속을 어기고 실제로 예외가 발생하면 → catch 기회 없이 즉시 `std::terminate()` 호출되어 프로그램 강제 종료
- 이동 생성자에 noexcept를 붙이는 기준: 내부에 힙 할당·복사 등 예외를 던질 수 있는 연산이 전혀 없을 때만 (단순 포인터 이전 등)

### 예외 전파와 스택
- 함수 내부에서 예외를 처리하지 않고 밖으로 던지면, 호출 스택을 따라 상위로 전파됨(stack unwinding)
- 어딘가 try-catch가 있으면 거기서 잡히고 프로그램은 계속 실행 가능, 아무도 안 잡으면 `std::terminate()` 호출로 프로그램 종료
- vector가 "내 상태는 예외 발생 전과 동일하게 유지하겠다"(강한 예외 보장)는 약속을 지키는 이유: 예외를 잡고 프로그램이 계속 살아남을 가능성이 있으므로

### Rule of 3 / Rule of 5 / Rule of 0
- Rule of 3: 동적 자원을 직접 관리하는 클래스는 소멸자, 복사 생성자, 복사 대입 연산자 3개를 함께 정의해야 함
- Rule of 5: Rule of 3 + 이동 생성자, 이동 대입 연산자 (C++11 이후 이동 시맨틱 포함)
- Rule of 0: 위 5개 함수를 아무것도 직접 정의하지 않는 것이 이상적
  - raw pointer 대신 unique_ptr, vector, string 등 표준 타입에 자원 관리를 위임
  - 컴파일러가 생성하는 기본 소멸자/복사/이동이 각 멤버의 것을 그대로 호출 → 안전하게 동작
  - 멤버가 복사 불가능한 타입(예: unique_ptr)이면, 컴파일러가 그 클래스의 복사 생성자를 자동으로 삭제 → 얕은 복사 실수가 런타임 크래시가 아니라 컴파일 에러로 잡힘
  - 표준 타입들의 이동 생성자는 이미 noexcept로 정의되어 있어서, Rule of 0을 따르면 noexcept 여부도 자동으로 해결됨 (직접 고민할 필요 없음)

### 정리: Rule of 3/5 vs Rule of 0
- Rule of 3/5: 직접 자원을 다루는 저수준 클래스(스마트 포인터 자체, 커스텀 컨테이너 등)에 필요
- Rule of 0: 실무에서 기본 지향점 — 표준 타입에 위임해서 다섯 함수 자체를 안 만드는 게 더 안전하고 관리 부담이 적음
