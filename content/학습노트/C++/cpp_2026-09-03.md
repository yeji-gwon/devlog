## 5-1. 다중 상속의 다이아몬드 문제

### 문제 상황
```cpp
class GameObject { public: int m_id; };
class Movable : public GameObject { };
class Damageable : public GameObject { };
class Enemy : public Movable, public Damageable { };

Enemy e;
e.m_id = 5;  // 컴파일 에러: 모호함(ambiguous)
```
- `Movable`과 `Damageable`이 각각 독립적으로 `GameObject`를 상속받으면, `Enemy`는 `GameObject` 서브오브젝트를 **두 개** 갖게 됨
- `e.m_id`가 `Movable`쪽 `m_id`인지 `Damageable`쪽 `m_id`인지 컴파일러가 판단할 수 없어 모호성 에러 발생

### 해결책: virtual 상속
```cpp
class Movable : public virtual GameObject { };
class Damageable : public virtual GameObject { };
class Enemy : public Movable, public Damageable { };
```
- `GameObject`를 `virtual`로 상속받으면, `Enemy`는 `GameObject`를 **하나만** 공유해서 가짐 → `e.m_id` 접근이 더 이상 모호하지 않음

### virtual 상속의 내부 동작
- **virtual 함수의 vptr**: "실제 객체 타입"을 찾아가 올바른 함수를 호출하기 위함
- **virtual 상속의 vbptr(virtual base pointer)**: "공유되는 기반 클래스가 메모리 상 어디 있는지" 찾아가기 위함
- 이름은 같은 `virtual` 키워드지만 목적은 다름 — 공통점은 "컴파일 타임에 확정 못 하는 것을 런타임에 간접 참조로 해결"한다는 점
- **일반 상속**: 기반 클래스가 고정된 오프셋에 위치 (컴파일 타임 확정)
- **virtual 상속**: 기반 클래스 위치를 가리키는 포인터(vbptr)를 통해 런타임에 찾아감 → 일반 상속보다 접근 비용이 더 듦 (간접 참조 한 단계 추가)

### 공유 기반 클래스는 누가 생성하는가
- **가장 마지막에 파생된 클래스(most-derived class)**가 virtual 기반 클래스의 생성을 책임짐
- `Enemy e;`라면: `Enemy`가 가장 먼저 `GameObject`를 직접 생성(단 한 번), 이후 `Movable`/`Damageable`은 자신이 새로 만들지 않고 이미 만들어진 `GameObject`를 가리키도록 vbptr만 세팅
- `Movable`을 단독으로 생성한다면(`Movable m;`), 이때는 `Movable`이 most-derived이므로 직접 `GameObject`를 생성 → "누가 만드는가"는 그 순간 최상위 클래스가 누구인지에 따라 동적으로 결정됨

### 실무 참고
- 다이아몬드 상속과 virtual 상속은 메모리 레이아웃이 복잡해지고 성능 오버헤드(간접 참조)가 있어 실무에서는 다이아몬드 구조 자체를 피하는 게 일반적
- 컴포넌트(HAS-A) 패턴이 다이아몬드 문제를 애초에 피하는 대안 (Movable, Damageable을 상속이 아니라 컴포넌트로 만들면 다이아몬드 자체가 발생하지 않음)

## 6. const와 참조

### const 멤버 함수
```cpp
class Player {
    int m_hp;
public:
    int Get_HP() const { return m_hp; }  // const 멤버 함수
};
```
- "이 함수는 `this`가 가리키는 객체를 변경하지 않는다"를 함수 시그니처 자체에 명시 → 컴파일러가 강제로 검증
- `const` 함수 내부에서 멤버 변수를 직접 수정하려 하면 **컴파일 에러** (noexcept처럼 "지켜지지 않는 약속"이 아니라 컴파일러가 실제로 강제하는 규칙)
- `const Player&`로 받은 객체에서는 `const`가 아닌 멤버 함수를 호출할 수 없음 (참조가 "안 바꾸겠다"고 약속했는데, non-const 함수는 "바꿀 수도 있다"고 간주되어 충돌 → 컴파일 에러)
- (참고) `mutable` 키워드: 멤버 변수에 붙이면 const 함수 안에서도 그 멤버만은 변경 가능 (캐시값, 카운터 등에 사용)

### const 참조 매개변수의 장점
```cpp
void Foo(const Player& player) { ... }
```
1. **성능**: 값 복사 비용 회피 (특히 큰 객체일 때 유리)
2. **안전성**: 함수가 실수로 원본 객체를 변경하는 것을 컴파일 타임에 방지
3. **가독성/문서화**: 함수 시그니처만 봐도 "이 함수는 읽기만 한다"는 의도가 명확히 드러남 → 호출자가 함수 내부 구현을 확인하지 않아도 안심하고 넘길 수 있음

### 참조 vs 포인터 매개변수 — 선택 기준
```cpp
void ProcessPlayer(const Player& player);  // 참조 버전
void ProcessPlayer(const Player* player);  // 포인터 버전
```
- **참조**: 문법적으로 "반드시 유효한 대상을 가리킨다"가 보장됨(nullptr 불가) → "이 값은 항상 존재해야 한다"는 계약. null 체크를 함수 내부에서 하지 않으므로, 호출자가 유효성을 스스로 보장해야 함
- **포인터**: nullptr일 수 있음 → "이 값은 없을 수도 있다(optional)"는 계약. 함수 내부에서 null 체크 필요, 호출자는 별도 검증 없이 넘겨도 됨(암묵적 합의)
- 판단 기준: "이 매개변수가 항상 존재해야 정상 동작하는가?" → 참조 / "없을 수도 있는 상황을 감안해야 하는가?" → 포인터
- (참고) `std::optional<T>`: C++17, 포인터 없이 "값이 있거나 없거나"를 전용 타입으로 표현. 포인터의 다른 의미(소유권, 배열 등)와 섞이지 않는 장점이 있으나, 게임 엔진 실무에서는 성능/메모리 이유로 포인터+nullptr 관용구가 여전히 많이 쓰임
