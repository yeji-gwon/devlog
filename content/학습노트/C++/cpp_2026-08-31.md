## 1. 메모리 관리 (스택 vs 힙)

### 핵심 개념
- 스택: LIFO 구조, 함수 호출 시 스택 프레임(매개변수/지역변수/복귀주소)이 push, 리턴 시 pop → 자동 생명주기 관리
- 힙: `new`/`delete`로 프로그래머가 직접 생명주기 관리

### 힙 할당이 느린 이유
- 스택: 스택 포인터 증감만으로 O(1) 할당/해제 (크기가 컴파일 타임에 결정)
- 힙: **free list**(빈 블록의 시작주소+크기를 관리하는 자료구조, 보통 연결리스트) 순회 탐색 필요 (first-fit, best-fit 등) → 탐색 비용 + 단편화(fragmentation) 관리 비용

### RAII (Resource Acquisition Is Initialization)
- 자원의 생명주기를 객체의 생명주기에 묶는 패턴
- 함수 중간 `return`으로 인한 `delete` 누락 → 메모리 누수 문제를 해결하는 핵심 아이디어
- 스마트 포인터가 대표적 구현체

## 2. 스마트 포인터

### unique_ptr vs shared_ptr
- unique_ptr: 유일 소유권
- shared_ptr: 공유 소유권, 컨트롤 블록(힙 할당)에서 참조 카운트 관리. 대입 시 카운트 증가, 소멸 시 감소, 0이 되면 객체 소멸

### 순환 참조 문제
- 두 shared_ptr가 서로 참조 → 카운트가 0이 되지 않아 누수
- weak_ptr로 해결: 소유권 없이 관찰만 함, `lock()`으로 유효성 확인 후 shared_ptr 획득

### new + shared_ptr 생성자 vs make_shared
| 항목 | `shared_ptr<T>(new T())` | `make_shared<T>()` |
|---|---|---|
| 힙 할당 횟수 | 2회 (객체, 컨트롤 블록 분리) | 1회 (한 블록에 통합) |
| 캐시 지역성 | 상대적으로 낮음 | 좋음 |
| 예외 안전성 | 상대적으로 취약할 여지 | 더 안전한 관용구 |
| **단점** | 없음(위 항목이 전부 단점) | weak_ptr가 오래 살아있으면 객체 메모리까지 묶여서 반환 안 됨 → 메모리 낭비 가능 |

### 스마트 포인터 사용 기준
- 소유권 단일 → `unique_ptr` (오버헤드 거의 없음, 기본값)
- 소유권 진짜 공유 필요 → `shared_ptr`
- 소유는 안 하고 관찰/순환참조 방지만 → `weak_ptr`

### 실무 패턴 예시: 리소스 캐시
- GameObject들이 `shared_ptr<Texture>` 소유
- ResourceManager는 `weak_ptr<Texture>`로 캐시 → 아무도 안 쓰면 자동 소멸, lock() 실패 시 재로드


### 스마트 포인터 vs raw pointer — 장단점 정리

#### unique_ptr vs raw pointer
- 크기: 둘 다 8바이트 (커스텀 deleter 없으면 오버헤드 사실상 없음)
- 장점: RAII로 메모리 누수/댕글링/이중 해제 예방
- 단점: 복사 생성자가 삭제(deleted)되어 있어 소유권 이전 시 반드시 `std::move()` 필요
  - 함수에 넘길 때 "소유권을 가져가야 하는지" 매번 판단해야 하는 불편함
  - 소유권 이전이 필요 없고 그냥 쓰기만 할 때는 `unique_ptr` 자체를 넘기지 말고 `.get()`으로 raw pointer를 넘기거나 참조(`&`)로 전달

#### shared_ptr vs raw pointer
- 크기: 16바이트(객체 포인터 + 컨트롤 블록 포인터) + 별도 컨트롤 블록
- 장점: 소유권 공유 시 자동 생명주기 관리
- 단점:
  - 참조 카운트 증감에 atomic 연산 사용 → 성능 오버헤드 (싱글스레드에서도 항상 발생, 컴파일러가 스레드 사용 여부를 알 수 없기 때문)
  - 순환 참조 구조에서 근본적으로 벗어나기 어려움 (weak_ptr로 회피는 가능하나 설계 자체를 다시 봐야 함)

#### 공통 단점: 소유권 관계가 코드 표면에서 흐려짐
- `shared_ptr`를 소유권이 아니라 단순 참조 목적으로도 남발하면:
  - 실제로는 해제되어야 할 객체가 예상치 못한 곳의 살아있는 카운트 때문에 계속 메모리에 남음
  - "이 객체가 왜 아직도 안 사라지지?" 같은 생명주기 버그는, raw pointer의 "왜 벌써 죽었지?"(댕글링) 버그보다 추적이 더 어려울 수 있음 (누가 소유자이고 누가 단순 참조자인지 코드만으로 구분 안 됨)
- 결론: 소유권이 필요한 곳에만 shared_ptr를 쓰고, 단순 참조는 raw pointer/참조/weak_ptr로 명확히 구분해서 쓰는 것이 중요

## 3. shared_ptr vs 게임 엔진의 수동 참조 카운팅

### 왜 게임 엔진은 shared_ptr 대신 수동 카운팅(AddRef/Release)을 쓰는가

1. **원자적 연산(atomic) 비용**
   - shared_ptr는 멀티스레드 안전을 위해 참조 카운트 증감에 **항상** atomic 연산 사용 (싱글스레드에서 써도 예외 없음 — 컴파일러가 스레드 사용 여부를 알 수 없기 때문)
   - atomic 연산은 캐시 라인 동기화(MESI 등) 오버헤드로 일반 정수 증감보다 느림
   - 수동 카운팅은 필요한 리소스에만 선택적으로 mutex/atomic 적용 가능

2. **메모리 크기**
   - shared_ptr: 16바이트(객체 포인터 + 컨트롤 블록 포인터) + 별도 컨트롤 블록
   - raw pointer + 수동 카운트: 8바이트로 더 가벼움

3. **메모리 풀/커스텀 얼로케이터와의 통합**
   - shared_ptr 컨트롤 블록은 표준 라이브러리 할당 방식에 묶여 있어 엔진 자체 메모리 풀과 통합이 번거로움
   - 수동 카운팅 오브젝트는 `operator new` 오버로드 등으로 엔진 메모리 풀에 자연스럽게 편입 가능

### 트레이드오프 정리
- shared_ptr: 안전성 자동 보장 ↔ 성능/메모리 통제력 희생
- 수동 카운팅: 성능/메모리 완전 통제 ↔ 안전성을 개발자 규율에 의존 (AddRef 누락 → 댕글링, Release 누락 → 누수, 중복 Release → use-after-free)
