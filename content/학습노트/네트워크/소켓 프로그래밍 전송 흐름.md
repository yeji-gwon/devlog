### 개요

서버에서 파일을 읽어 클라이언트로 전송하는 상황을 예로 들어 단계별로 정리한다. (유튜브 강의 참고)

>**결론부터** : 파일 전송이 느려 보이는 병목의 원인은 대부분 네트워크가 아니라 클라이언트(수신 측)가 `recv()`를 얼마나 빨리 호출해서 버퍼를 비워주는가에 있다. 이 노트는 그 이유를 두 단계로 나눠서 설명한다.



전체 과정은 두 파트로 나뉜다.

1. **① 포장 단계** - 서버가 보낼 데이터를 어떻게 잘라서 실어 보내는가 (send → 세그먼트 → 패킷 → 프레임)
2. **② 통제 단계** - 상대방이 그 데이터를 받을 준비가 됐는지 확인하며 보낼지 말지를 결정하는 과정 (ACK, 윈도우 사이즈)

①이 데이터를 어떻게 포장해서 보내는가 라면, ②는 포장한걸 지금 보내도 되는가를 다루는 것이다. 그리고 이 둘은 전송 → 확인 → (가능하면) 전송 → ... 반복되는 사이클이다.


### ① 포장 단계 - 데이터가 세그먼트·패킷·프레임이 되는 과정

1. (서버) `send()`를 호출하면 응용 프로그램 버퍼의 데이터가 소켓 송신 버퍼로 `len`만큼 복사된다. 
	```
	int send(SOCKET s, const char* buf, int len, int flags)
	```

2. (TCP) 송신 버퍼에 쌓인 데이터는 MSS 단위로 나뉘어 **세그먼트**가 된다. 
   
	- MSSMaximum Segment Size): TCP가 헤더를 제외하고 한 번에 실어 보낼 수 있는 순수 데이터(페이로드)의 최대 크기 (byte)
	  
	- 세그먼트 = TCP 헤더 + 페이로드
	  
	- TCP 헤더 = 시퀀스 번호 + ACK 번호 + 출발지/목적지 포트 + 플래그 + 윈도우 사이즈 + 체크섬
	  
3. (IP) 세그먼트에 IP 헤더가 붙어 **패킷**이 된다. 

4. (링크) 패킷에 이더넷 헤더와 트레일러가 붙어 **프레임**이 된다. 

5. (참고) 프레임은 라우터를 거칠 때마다 벗겨지고 새로 만들어지지만(재캡슐화), 패킷은 출발지에서 목적지까지 논리적으로 그대로 유지된다.

이렇게 만들어진 프레임 하나(=세그먼트 하나)가 클라이언트에 도착하면, ② 단계가 시작된다.


### ② 통제 단계 - ACK와 윈도우 사이즈로 보낼지 말지 결정

1. 서버는 세그먼트를 `send()`한 뒤, 그 시퀀스 번호에 대한 **ACK가 올 때까지 대기**한다 → 이 대기 시간이 **속도 지연**의 원인 중에 하나이다.

2. 클라이언트는 세그먼트를 받으면 ACK를 돌려보내는데, 이때 자신의 **윈도우 사이즈**(수신 버퍼 여유 공간)도 함께 실어 보낸다.

3. 서버는 ACK를 받으면, 다음 데이터를 보내기 전에 이 윈도우 사이즈를 확인한다.
   
	- 보낼 데이터 크기 <= 윈도우 사이즈 → 바로 ①로 돌아가 다음 세그먼트 전송
	  
	- 보낼 데이터 크기 > 윈도우 사이즈 → **wait**
	  
		- 클라이언트가 `recv()`를 호출해 수신 버퍼를 비우면 → 윈도우 사이즈 확보 → 서버는 wait 상태에서 벗어나 ①로 복귀
		  
		- 클라이언트가 `recv()`를 계속 호출하지 않으면 → 서버의 송신 버퍼까지 꽉 참 → `send()`가 blocking 모드면 대기 상태에 빠지고, non-blocking 모드면 `EAGAIN` / `EWOULDBLOCK` 에러를 반환

>따라서 **클라이언트의 `recv()` 처리 속도가 네트워크 수신 속도보다 빨라야** 윈도우 사이즈가 항상 여유있게 유지되고, 결과적으로 서버의 wait(전송 지연)을 최소화할 수 있다.


### 핵심 포인트

- **속도 지연의 두 원인** : ① 매 세그먼트마다 ACK를 기다리는 대기 시간 지연 + ② 윈도우 사이즈 부족으로 인한 wait

- **병목의 실제 위치** : 대부분 네트워크 자체가 아니라 **수신 측(클라이언트) 애플리케이션의 `recv()` 처리 속도**

- **실무 원칙** : `recv()`는 최대한 빠르게 반복 호출해서 버퍼를 비우고, 무거운 처리(파싱/저장 등)는 별도 큐, 스레드로 분리해 `recv()` 호출 자체가 지연되지 않게 한다.
