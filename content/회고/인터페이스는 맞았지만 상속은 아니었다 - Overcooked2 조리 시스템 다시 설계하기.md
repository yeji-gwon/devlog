## 0. 개요

Overcooked2를 유지보수 관점에서 다시 들여다봤다. 재료(`CIngredient`)와 조리대(`CInteract`계열), 이 두 축의 클래스 구조를 그때 짠 그대로 열어봤고, 지금 기준으로 뭐가 걸리는지 정리해본다. 결론부터 말하면 둘 다 같은 패턴을 갖고 있었다. **인터페이스로 능력을 나눈 것 자체는 괜찮은 선택이었는데, 그걸 표현하는 방식(상속, 캐스팅, enum 분기)이 확장을 막고 있었다.**

왜 이게 문제냐면, 재료나 조리대가 하나씩 늘어날 때마다 그 종류를 확인하는 캐스팅이나 분기도 어딘가에서 같이 늘어나야 하는 구조였기 때문이다. **새 기능을 추가하는 일이 새 코드를 보태는 일이 아니라, 기존 코드 여러 곳을 찾아 고치는 일**이 되어버린다. 이게 지금 이 구조가 **유지보수 관점에서 나쁘다**고 보는 기준이다.

돌이켜보면 그때는 컴포넌트라는 개념을 막 배운 시점이라 뭘 컴포넌트로 분리해야 하는지, 얼마나 잘게 쪼개야 하는지에 대한 감이 아직 없었다. 그래서 FSM이든 조리대의 능력이든, 새로 배운 컴포넌트 보다는 익숙한 상속으로 표현하는 쪽을 택했던 것 같다.


## 1. 요구사항 분석

Overcooked2는 제한 시간 안에 손님의 주문에 맞춰 요리를 완성해 제공하는 협동 요리 시뮬레이션 게임이다. 나는 이 중 재료 손질, 조리, 접시 세척, 서빙 과정에서 플레이어가 상호작용하는 대상을 맡았다.

이 파트에서 요구되는건, 도마, 프라이팬, 냄비, 세척대처럼 서로 다른 시간 기반 처리를 하는 조리대가 여럿 있어야 했고, 재료는 그 조리대들을 거치면서 상태(날 것 → 썬 것 → 조리 된 → 탐)가 계속 바뀌어야 했다. 그리고 게임 특성상 새로운 재료나 조리대가 계속 추가될 걸 감안해야 했다. **확장을 전제로 설계해야 하는 파트**였다.

### 1. 재료 분석

#### 문제 1 - `CIngredient`가 재료 데이터와 FSM을 겸함

```cpp
// Client/Header/CIngredient.h
class CIngredient : public CInteract
{
	//...
protected:
	INGREDIENT_TYPE			m_eIngredientType;	// 재료 종류 (재료 데이터)
	IState*					m_pCurrentState;	// 현재 State* (FSM)
	_bool					m_bLocked;			// 조리 중 잠금 여부
	//...
};
```

"재료가 무엇인가(종류)"와 "재료가 지금 어떤 상태 처리 로직을 타야 하는가(FSM)"가 한 클래스에 뒤섞여 있다. `CTomato`, `CFish` 같은 파생 클래스 20여 개가 전부 이 조합을 그대로 상속받다 보니, FSM 쪽만 손대고 싶어도 `CIngredient` 전체를 건드리게 된다.
