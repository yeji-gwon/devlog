[[인터페이스는 맞았지만 상속은 아니었다 - Overcooked2 조리 시스템 다시 설계하기]]에서는 기존 조리 시스템을 다시 보면서 컴포지션을 1차 개선안으로 잡았다.

조리대의 역할을 `IPlace`, `IChop`, `IWash` 같은 인터페이스 상속으로 표현하고, 호출부에서는 다시 `dynamic_cast`로 구체 역할을 확인하고 있었다. 그래서 변화하는 기능을 컴포넌트로 분리해 조합하면 기존 코드에 퍼지는 변경을 줄일 수 있다고 생각했다.

그런데 개선안을 구체화하려고 코드를 더 보다 보니 생각이 조금 바뀌었다.

> 컴포지션이 더 유연하다는 이유만으로 지금 구조를 바꾸는 게 맞을까?

기존 코드에 이미 있는 추상화를 제대로 사용하는 것만으로 해결할 수 있는 문제도 있었고, 컴포넌트보다 데이터로 옮기는 편이 자연스러운 부분도 있었다.

이번에는 `상속 → 컴포지션`을 답으로 정해놓지 않고 **실제로 무엇이 변하고, 그 변화가 어디까지 퍼지는지**를 기준으로 다시 봤다.

### 조리대 - 문제는 상속보다 추상화를 사용하는 방식에 가까웠다

플레이어의 상호작용 코드를 다시 보면 다음과 같다.

```
if (dynamic_cast<IChop*>(m_pCursorStation))
{
    m_pIChop = dynamic_cast<IChop*>(m_pCursorStation);

    if (m_pIChop->Enter_Process())
    {
        // ...
    }
}
else if (dynamic_cast<IWash*>(m_pCursorStation))
{
    m_pIWash = dynamic_cast<IWash*>(m_pCursorStation);

    if (m_pIWash->Enter_Process())
    {
        // ...
    }
}
```

1편에서는 이 코드를 보고 역할을 컴포넌트로 분리하는 방향을 생각했다.

그런데 인터페이스 계층을 다시 보면 이미 공통 기반인 `IProcess`가 있다.

```
IProcess
├─ IChop
├─ ICook
├─ IWash
└─ IExtinguish
```

플레이어가 필요한 것이 결국 Process를 시작하는 것이라면, 현재 대상이 `IChop`인지 `IWash`인지 플레이어가 직접 구분할 필요가 있는지부터 다시 생각해볼 수 있다.

```
처음 판단

dynamic_cast 분기가 늘어난다
→ 상속 구조가 문제다
→ 컴포지션으로 바꾼다


다시 본 판단

IProcess라는 공통 추상화가 이미 있다
→ 호출부가 IChop / IWash를 다시 구분하고 있다
→ 먼저 IProcess만 사용하도록 만들 수 있는지 본다
```

### 구조 전체를 바꾸기 전에 할 수 있는 것

개념적으로는 대상에게 공통 Process를 요청하는 형태를 생각할 수 있다.

```
IProcess* pProcess = pTarget->Get_Process();

if (pProcess)
{
    pProcess->Enter_Process();
}
```

이 코드는 현재 프로젝트에 존재하는 구현이 아니라 개선 방향을 설명하기 위한 예시다. 실제로 적용한다면 Process를 어떻게 제공할지, 포인터와 객체의 수명을 어떻게 관리할지 등을 더 정해야 한다.

여기서 중요한 건 `Get_Process()`라는 함수 자체가 아니라 **Player가 구체 Process의 종류를 알지 않도록 하는 것**이다.

그렇게 할 수 있다면 새로운 Process가 추가돼도 Player의 분기를 반드시 같이 수정할 필요는 없다.

```
기존

새 Process 추가
    ↓
Station 구현
    ↓
Player가 새 타입을 알아야 함
    ↓
Player 분기 수정


개선 방향

새 Process 추가
    ↓
Station이 공통 IProcess 제공
    ↓
Player는 IProcess만 사용
```

이 문제만 놓고 보면 전체 조리대를 컴포넌트 구조로 바꾸는 것보다 이미 있는 `IProcess`를 제대로 활용하는 편이 변경 범위가 작다.

1편에서 세운 개선안이 완전히 틀렸다기보다 **문제보다 큰 해결책을 먼저 생각한 셈**이었다.

### 그래도 인터페이스 사이의 결합은 남아 있다

호출부만 정리한다고 모든 문제가 해결되는 것은 아니다.

`IPlace::Set_Empty()`를 보면 `IPlace`가 `IProcess`의 존재를 확인한다.

```
virtual void Set_Empty()
{
    m_bFull = false;
    m_pPlacedItem = nullptr;

    if (dynamic_cast<IProcess*>(this))
        dynamic_cast<IProcess*>(this)->Set_Progress(0.f);
}
```

물건이 제거됐을 때 Process의 진행도도 초기화해야 한다는 규칙이 `IPlace` 안에 들어가 있다.

여기서는 두 가지를 따로 봐야 했다.

- `IPlace`와 `IProcess`라는 역할을 나누는 것
    
- 두 역할의 상태 변화를 누가 조정할지 정하는 것
    

첫 번째는 했지만 두 번째는 명확하지 않았다. 그래서 `IPlace`가 런타임에 다른 역할의 존재를 확인하게 됐다.

이런 관계가 많아지고 역할의 조합이 계속 늘어난다면 그때는 컴포지션의 이점이 커질 수 있다. Station이 `PlaceComponent`, `ProcessComponent`를 소유하고 둘의 관계를 명시적으로 조정하는 방식도 생각할 수 있다.

다만 컴포지션으로 바꾸면 컴포넌트의 생성과 수명, 상태 공유, 유효하지 않은 조합을 어떻게 막을지 같은 문제도 새로 생긴다.

그래서 지금 다시 구현한다면 인터페이스 상속을 발견하는 즉시 컴포지션으로 바꾸기보다, **독립적으로 조합되어야 하는 기능이 실제로 얼마나 많은지**부터 확인할 것 같다.

### 재료 - 컴포넌트보다 데이터에 가까운 차이도 있었다

재료 쪽도 처음에는 비슷하게 생각했다.

`CIngredient`의 파생 클래스를 보면서 재료마다 다른 기능을 별도의 컴포넌트로 분리하면 좋겠다고 생각했다.

그런데 실제 구현을 비교해보니 `CTomato`, `CCucumber`, `CFish`, `CLettuce`, `CShrimp` 등 여러 재료의 코드가 거의 같은 형태였다.

렌더링에서도 비슷한 코드가 반복된다.

```
int iIndex = (RAW != m_eCookState) ? 1 : 0;

m_vecTextureCom[i]->Set_Texture(iIndex);
```

확인한 코드에서는 이 재료들의 차이가 고유한 행동보다 사용하는 리소스와 종류별 규칙에 더 가까웠다.

그렇다면 기능을 컴포넌트로 하나 더 만드는 것보다 같은 행동을 공유하고 차이만 데이터로 표현하는 편이 단순할 수 있다.

예를 들면 다음과 같은 형태다.

```
struct SIngredientData
{
    INGREDIENT_TYPE eType;

    wstring rawTexture;
    wstring processedTexture;

    // 재료별 규칙...
};
```

정확한 데이터 구조는 실제 요구사항을 다시 정한 뒤 결정해야겠지만, 중요한 것은 **새 재료마다 비슷한 파생 클래스를 하나 더 만드는 것이 정말 필요한가**를 먼저 확인하는 것이다.

고유 행동이 있는 재료라면 별도 구현이 필요할 수 있다. 반대로 차이가 데이터뿐이라면 클래스보다 데이터로 표현하는 편이 자연스럽다.

### 클래스와 enum으로 정체성을 두 번 표현하고 있었다

State 코드를 보다 눈에 띈 부분도 있었다.

```
if (CIngredient::TOMATO == eType &&
    dynamic_cast<CTomatoSoup*>(pIngredient))
{
    return;
}
```

그런데 `CTomatoSoup`의 초기화에서는 타입을 다음처럼 설정한다.

```
m_eIngredientType = TOMATOSOUP;
```

현재 코드만 놓고 보면 `CTomatoSoup`이면서 `eType == TOMATO`인 경우가 만들어지지 않기 때문에 위 조건은 실행되기 어렵다.

작성 당시 어떤 변경을 거쳐 이 코드가 남았는지는 지금 코드만으로 알 수 없다. 다만 현재 구조에서는 재료의 정체성을 C++ 클래스와 `INGREDIENT_TYPE` 두 가지 방식으로 표현하고 있고, 둘의 일관성을 사람이 맞춰야 한다.

```
CTomato       ↔ TOMATO
CCucumber     ↔ CUCUMBER
CTomatoSoup   ↔ TOMATOSOUP
```

처음에는 `CTomatoSoup`처럼 별도 클래스가 있는 것을 보고 고유 행동을 컴포넌트로 분리해야 한다고 생각했다.

하지만 다른 재료 구현까지 비교해보니 비슷한 렌더링과 상태별 처리가 반복되는 부분도 있었다. 하나의 클래스만 보고 개선 방향을 정하기보다 여러 구현을 비교해서 **실제로 달라지는 것이 행동인지 데이터인지**부터 확인할 필요가 있었다.

### 재료를 데이터화해도 종류별 분기가 남으면 문제는 그대로다

재료 클래스만 데이터화한다고 끝나는 것도 아니다.

State에는 재료 종류별 분기가 남아 있다.

```
if (CIngredient::TOMATO == eType ||
    CIngredient::LETTUCE == eType ||
    CIngredient::CUCUMBER == eType ||
    CIngredient::FISH == eType ||
    CIngredient::SHRIMP == eType)
{
    pIngredient->ChangeState(new IDoneState());
}
```

이 코드에서 State는 현재 상태의 동작뿐 아니라 어떤 재료가 어떤 규칙을 따르는지도 알고 있다.

새 재료가 추가될 때마다 이런 목록을 찾아 수정해야 한다면 재료 클래스를 데이터화해도 변경 지점은 충분히 줄어들지 않는다.

따라서 재료별 차이를 데이터로 옮긴다면 상태 전이에 필요한 규칙도 같이 관리할 필요가 있다.

예를 들어 재료마다 필요한 처리 여부나 가능한 상태 전이 같은 정보를 데이터로 표현하고, State에서는 특정 재료 이름을 직접 나열하지 않는 방향을 생각할 수 있다.

여기서 중요한 건 `bool` 몇 개를 추가하는 식의 구현 자체가 아니다.

**새 재료를 추가할 때 기존 State 코드까지 수정해야 하는가?**

이 질문을 기준으로 규칙을 어디에 둘지 결정하는 것이 더 중요하다.

### 다시 정리한 개선 순서

코드를 더 본 뒤에는 1편에서 생각한 `컴포지션 중심의 재설계`보다 다음 순서로 접근하는 편이 낫다고 생각했다.

1. **기존 추상화를 먼저 제대로 사용할 수 있는지 확인한다.**  
    `IProcess`가 이미 있다면 Player가 `IChop`, `IWash`를 각각 확인하지 않고 공통 인터페이스만 사용하도록 만들 수 있는지 본다.
    
2. **행동보다 데이터 차이가 큰 객체는 데이터화를 검토한다.**  
    재료 파생 클래스가 대부분 같은 행동을 공유한다면 클래스 계층을 늘리기 전에 차이를 데이터로 옮길 수 있는지 본다.
    
3. **종류별 규칙이 흩어져 있다면 한곳에서 관리할 수 있는지 본다.**  
    새 재료를 추가할 때 여러 시스템의 `if`문을 찾아다니지 않도록 규칙의 위치를 정한다.
    
4. **독립적인 기능 조합이 실제로 늘어날 때 컴포지션을 검토한다.**  
    기능이 여러 오브젝트에서 자유롭게 조합되고 역할 사이의 의존도 계속 증가한다면 컴포넌트 분리로 얻는 이점과 추가되는 복잡도를 비교한다.
    

이렇게 보면 기존 코드를 전부 바꾸지 않고도 작은 문제부터 줄여갈 수 있다.

### 다시 코드를 보면서 바뀐 기준

처음 프로젝트를 만들 때는 주로 이런 질문을 했다.

```
이 객체는 무엇인가?
어떤 부모를 상속해야 할까?
어떤 인터페이스가 필요할까?
```

1편에서는 여기서 상속보다 컴포지션을 활용하는 방향으로 생각을 넓혔다.

이번에 개선안까지 다시 검토하면서는 질문의 순서가 조금 달라졌다.

```
무엇이 변할까?
      ↓
그 변화가 현재 어디까지 퍼질까?
      ↓
왜 그 코드까지 같이 바뀌어야 할까?
      ↓
기존 구조에서 변경 범위를 줄일 수 있을까?
      ↓
그래도 부족하다면 구조를 어떻게 바꿀까?
```

조리대에서는 이미 존재하는 `IProcess`를 제대로 활용하는 것이 먼저였고, 확인한 재료들에서는 컴포넌트보다 데이터화가 더 자연스러운 부분이 있었다. 독립적인 기능 조합이 계속 늘어나는 부분에서는 여전히 컴포지션이 선택지가 될 수 있다.

결국 상속, 인터페이스, 컴포지션 중 하나를 먼저 고르는 것보다 **새로운 요구사항 하나가 들어왔을 때 기존 코드의 어디가, 왜 함께 바뀌어야 하는지**를 먼저 보는 편이 나에게는 더 이해하기 쉬웠다.
